# spec §6.3 噩梦路径：完整度账本

**887 个单元测试证明的是「零件对」，没有证明「产品能用」。** §6.3 是 spec
自己的完整度清单——用它意味着「完整」有客观定义，而不取决于谁的判断。

本目录是那张清单的**可执行形态**。下表是账本：每一条要么指向断言它的地方，
要么明写「未覆盖」。**不允许出现「大概覆盖了」这种状态**。

| # | 噩梦路径 | 状态 | 断言在哪 |
| --- | --- | --- | --- |
| 1 | 未下载目录的整体改名/移动 | ⬜ 未覆盖 | 需占位符层（M3d/M4） |
| 2 | 离线修改 + 重连 | ✅ | `journey.sh` |
| 3 | hydration 中文件被编辑/被释放 | ⬜ 未覆盖 | 需占位符层 |
| 4 | 占位层与真相层不一致（投影重建） | ⬜ 未覆盖 | 需占位符层 |
| 5 | A 改名、B 编辑，在 hub 汇合 | ✅ | `journey.sh`（引擎收敛后通过，见下） |
| 6 | Linux 客户端以 server 角色运行 | ⬜ 未覆盖 | 角色本身有测试（M2d），整条路径没端到端跑过 |
| 7 | ★ 全库索引不触发水化 | ✅ | `arca-agentd` 的 `hydration`/`provider` 单元测试（M3c，策略层） |
| 8 | ★ 笔记打开风暴 | ⬜ 未覆盖 | 队列限流有单测，端到端需占位符层 |
| 9 | ★ `.gitignore` 反选写法 | ✅ | `arca-git/tests/nightmare.rs`（M1c） |
| 10 | ★ 清单与实体一致性 | ❌ **不成立** | `arca checkout` 已实现，但**历史版本字节从未留存**，见下 |
| 11 | ★ 多 hub 故障隔离 | ✅ | `arca-cli/tests/multi_hub.rs`、`arca-agentd/tests/multi_hub_isolation.rs`（M2d） |
| 12 | 数据集搬迁零重传 | ❌ **失败** | `journey.sh`——`register` 报 `hub_instance_id` 不符，见下 |

## 两个已确认的阻断项

### 第 5 条：`arca sync` 曾有两个引擎，改名检测只在其中一个里 —— **已修**

- `file://` → `sync_lib::sync`（`sync.rs:285`）——**没有改名检测**
- `http://` → `sync_lib::sync_transport`（`sync.rs:869`）——**有** `detect_renames`

后果：同一个改名，在 `file://` 上退化成「上传新文件 + tombstone 旧文件」——
hub 上新建 item_id（**违反 I7 身份跨改名稳定**）、内容被全量重传、版本链分叉，
协作者还要再下载一遍一模一样的字节。而 `file://` 是 CLAUDE.md 说的「一等用户」
路径（Linux/CI 只用手动模式）。

这正是 M2d 评审命名过的那类问题：「同一个抽象下两条实现分叉，正是 `Transport`
当初要消除的」。

**修法**：CLI 的 `file://` 分支改走 `sync_transport + LocalTransport`，两种 hub
同一个引擎。演练重跑通过。

修之前我担心性能：`sync()` 有批量提交（`Batch`/`AppendBatch`）而 `sync_transport`
没有（M2c 归档记过「`sync_transport` 的批量化未完成」），换过去会让一万文件基准回退。
**测量推翻了这个假设**——基线 239.3s、改后 240.0s，差 0.7s（噪声级别）。原因很简单：
240 秒里 238 秒花在 `adopt`（归档）上，而 `adopt` 压根不走 `sync`。

顺带发现：**一万文件基准早就在失败**（239s vs 120s 预算），与本次改动无关。
它是 `#[ignore]` 的、不进 CI，所以一直没人看见。瓶颈在 `adopt`，不在同步。

### 第 12 条：数据集搬迁在 `register` 一步就失败

```
photo 已有 dataset.toml，其 hub_instance_id "fd15…" 与本次解析出的 "c864…" 不符
```

搬迁场景是：把 `photo/`（含 `.arca/`）整体移到另一个 git 仓库，然后在新 vault 里
`register` 同一个 hub。`dataset.toml` 里记着原 hub 的 `instance_id`，而新 vault 的
`.gitarca` 解析出的是另一个——两者对不上就拒绝（I5：绝不猜测）。

**拒绝本身是对的**，但它让 spec §6.3 第 12 条承诺的「搬迁后身份/清单/hub 归属
全部复位、零重传」走不通：目前没有任何一条命令能表达「这就是同一个数据集，
只是换了个仓库」。缺的是搬迁通路本身，不是那道校验。

> **订正**：本账本此前把第 12 条标为 ✅ 是错的——前两次演练都在第 5 条就停了，
> 第 12 条**从未真正跑到过**。标记依据必须是「跑过并通过」，不是「写了断言」。

### 第 10 条：历史版本的字节从未被保留过

hub 存储根里只有 `files/`（当前版本）、`index/`、`items/`、`journal/`——
**`.arca/chunks/` 根本不存在**。`items/` 的版本链记的是元数据，那些哈希对应的
字节没有任何地方保存。所以任何指向旧版本的清单都还原不了。

格式契约已于 `FORMAT.md` §7.1/§8 定稿（`chunks` 字段 + 拼回纪律），
缺的是**写入侧**。

## `adopt` 性能：两处真因，一处已修

一万文件基准 **238s vs 120s 预算**。分相位测量把范围钉死了：

```
800 文件（release）
  adopt（含上传）        18.56s   → 23.2ms/文件
  sync （第二次，无事可做） 0.07s
  status                   0.06s
```

**全部成本都在上传路径**；扫描与读远端对 800 文件几乎免费。

### 已修：`commit` 的 O(n²)

`LocalTransport::commit` 每次都读一遍全部远端状态做身份校验，
`commit_batch` 内部又对每条请求全扫一遍 `working_remote`。两处都是 O(n²)。

修法：`sync_transport` 的上传改走 `commit_batch`（批次被拒时逐条回退，
语义与逐条提交完全一致），并在 `commit_batch` 里建 `item_id → path` 倒排索引
增量维护。**效果：每文件成本从随规模上升变成持平**——

| | 修前 | 修后 |
| --- | --- | --- |
| 200 文件 | 39.8ms/个 | 25.1ms/个 |
| 800 文件 | **56.5ms/个** | **23.0ms/个** |

顺带关掉 M2c 评审记的「`commit_batch` 生产路径零调用者」。

### 未修：`F_FULLFSYNC` 的常数

剩下的是每文件 **~23ms 的常数**，10000 文件 = 234s。真因：

| | 每次 |
| --- | --- |
| 普通 `fsync` | **0.08ms** |
| **`F_FULLFSYNC`** | **4.15ms** |

**Rust 的 `File::sync_all()` 在 macOS 上就是 `F_FULLFSYNC`**（真正的设备屏障，
不是普通 fsync）。每文件 4–5 次原子写（`files/` + `items/` + `index/` + journal）
× 4.15ms ≈ 20ms，与实测 23ms/文件吻合。

**修的方向**：内容与指针的持久化要求不同。不变量是「**字节落盘先于指针发布**」
——它约束的是*顺序*，不是*每个都各自设一道屏障*。所以：

- 内容文件：仍需逐个 fsync（跨平台上 Linux 的 `fsync` 只覆盖单个文件，
  不能靠一次屏障蒙混）
- `items/` + `index/` + journal 这些**指针**：整批共用一次屏障，
  在内容全部落盘之后、批次收口时做一次

4–5 次屏障/文件 → 1 次/文件，预期 234s → 约 60s，进预算。

**但算术表明「少做一次屏障」不够**——必须降到每文件 ≤2 次：

| 每文件 `F_FULLFSYNC` | 10000 文件 | 预算 120s |
| --- | --- | --- |
| 4（现状） | 166s ＋其它开销＝实测 234s | ✗ |
| 3 | 124.5s | ✗ **仍然超** |
| 2 | 83s | ✓ |

一次上传现在写 4 个文件：`files/<path>`（内容）、`items/<id>.jsonl`、
`index/<key>.json`、journal 事件。**只有第一个是「内容」**，后三个都是指针。

### 这已经不是纯优化，是一次持久化策略取舍

要降到 2 次，只能让**三个指针共用一次屏障**（或干脆不各自 fsync）。
可行性论证与风险：

- **不变量仍然成立**：I1 要求的是「内容落盘先于指针发布」——约束*顺序*，
  不约束指针彼此之间。指针丢失的后果是「内容成为孤儿」，
  而 **M2c 已经明确接受过这个取舍**（「批量提交在磁盘上不是全有全无……
  实现者选了『让 fsck 能看见孤儿』」）。
- **新增的风险是「指针 rename 落盘了、但它的内容没落盘」**——文件存在却是
  半截/全零。这是一个**新的**失败形态，现在没有。
- 缓解它的理由：这三个都是 JSON/JSONL，**读取侧一律解析**，
  半截内容会解析失败而不是被当成有效数据（I5 的既有纪律）。
  所以它是**可检出**的，不是静默损坏。

**这是一个需要人拍板的决定**，不是机械修复：它拿「可检出的新失败形态」
换「一万文件从 234s 降到 ~83s」。我没有单方面做这个决定。

配套要求（无论怎么定）：**崩溃注入测试**——在屏障前后各注入一次崩溃，
断言「内容在、指针不可见」与「指针在、内容也在」，绝不能只看基准变快。

### 三次诊断，两次错——记下过程

1. 第一次：归因 fsync。**方向对**。
2. 第二次：用 Python 的 `os.fsync` 量了一下，得 0.03ms/次，据此判定
   「fsync 与此无关」，把一条正确的诊断"订正"成了错误的。
   **错在量错了对象**——Python 的 `os.fsync` 是普通 `fsync()`，
   而 Rust 的 `sync_all()` 在 macOS 上是 `F_FULLFSYNC`，两者差 52 倍。
3. 第三次：分相位定位 + 直接对比两种 fsync，才拿到真相。

> **教训升级**：「性能瓶颈要量」还不够——**要量的必须是生产代码真正调用的
> 那个原语**。拿一个同名但语义不同的东西去量，比不量更危险：它会给你一个
> 有数字撑腰的错误结论。

## 一次清理留到下一轮

旧 `file://` 引擎收敛掉之后，`sync.rs` 里有四个私有 helper
（`prepare_upload` / `execute_download` / `execute_tombstone_content` /
`remove_index_record`）只剩测试在用，文件顶部因此挂了 `#![allow(dead_code)]`。

**没有在同一轮里删掉它们**：移除会牵动一批测试的构造方式，与「收敛引擎」
是两件事，混在一起会让这次改动难以复核。留给一次专门的清理。

（我在这一轮里试着顺手删过，结果是反复试错——clippy 报的「从未使用」来自
非测试构建，而那几个函数其实是测试在用。教训：**清理死代码要看
`--all-targets` 的结论，不是 lib 构建的**。）
