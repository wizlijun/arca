# spec §6.3 噩梦路径：完整度账本

**887 个单元测试证明的是「零件对」，没有证明「产品能用」。** §6.3 是 spec
自己的完整度清单——用它意味着「完整」有客观定义，而不取决于谁的判断。

本目录是那张清单的**可执行形态**。下表是账本：每一条要么指向断言它的地方，
要么明写「未覆盖」。**不允许出现「大概覆盖了」这种状态**。

| 1 | 未下载目录的整体改名/移动 | ⬜ 未覆盖 | 需占位符层（M3d/M4） |

## 两个已确认的阻断项

### 第 5 条：`arca sync` 有两个引擎，改名检测只在其中一个里

- `file://` → `sync_lib::sync`（`sync.rs:285`）——**没有改名检测**
- `http://` → `sync_lib::sync_transport`（`sync.rs:869`）——**有** `detect_renames`

后果：同一个改名，在 `file://` 上退化成「上传新文件 + tombstone 旧文件」——
hub 上新建 item_id（**违反 I7 身份跨改名稳定**）、内容被全量重传、版本链分叉，
协作者还要再下载一遍一模一样的字节。而 `file://` 是 CLAUDE.md 说的「一等用户」
路径（Linux/CI 只用手动模式）。

这正是 M2d 评审命名过的那类问题：「同一个抽象下两条实现分叉，正是 `Transport`
当初要消除的」。

**修法有取舍**：直接把 `file://` 换成 `sync_transport + LocalTransport` 是最干净的
收敛，但 `sync()` 有批量提交（`Batch`/`AppendBatch`）而 `sync_transport` 没有
（M2c 归档记过：「`sync_transport` 的批量化未完成」），换过去会让一万文件基准回退。
正解是**收敛 + 给 `sync_transport` 补 `commit_batch`**，两件事一起做。

### 第 10 条：历史版本的字节从未被保留过

hub 存储根里只有 `files/`（当前版本）、`index/`、`items/`、`journal/`——
**`.arca/chunks/` 根本不存在**。`items/` 的版本链记的是元数据，那些哈希对应的
字节没有任何地方保存。所以任何指向旧版本的清单都还原不了。

格式契约已于 `FORMAT.md` §7.1/§8 定稿（`chunks` 字段 + 拼回纪律），
缺的是**写入侧**。

## 为什么这个演练还没进 CI

因为它现在是**红的**——第 5 条（续）会失败。这是有意的：它把一个真实缺陷变成了
可执行断言。等两个阻断项修完再接进 CI；在那之前，**不要为了让它变绿而放松断言**。
