## 偏离原规格的决定

这一节是本文档存在的主要理由。

### MSRV 从 1.75 改为 1.85（`46b381e`）

骨架阶段我随手写了 `rust-version = "1.75"`。实测 `cargo +1.75 check` **直接失败**：
blake3 的传递依赖 `constant_time_eq 0.4.2` 需要 edition2024，而它要求 Cargo 1.85+。

结论：**声明一个实测不成立的 MSRV 比不声明更糟**。改成实测通过的 1.85，
并在 CI 里加了固定 1.85 的构建门禁，让今后任何一次 `cargo update` 撞破这条线时大声失败。

### 新增 `arca-store` crate（`429c482`，spec §11.1 与 README 已同步）

原 crate 清单里没有它，fsck 本来计划放在 `arcad`。重新判定的理由：**读写 hub 存储根的
消费者有两个**——M2 的 arcad，以及 M1 的 `file://` 直连同步与 `arca verify`。两者都存在，
这段逻辑就属于它们共同的下层，不该住进其中任何一个（daemon 依赖 CLI 或 CLI 依赖 daemon
都是错的方向）。

与 `arca-core` 的分工：core 是 sans-io 状态机决定「该做什么」，`arca-store` 负责「怎么落盘」。

### 许可证分层（`503207e`、`7483625`）

库与客户端 MIT，服务端 `arcad` AGPL-3.0-only。依赖方向单向：MIT 库可进 arcad，反之不行。
**架构后果**：两端共用的逻辑必须留在 MIT crate 内，否则会被 AGPL 传染而无法在客户端复用。
这条与「arca-core 两端共用」是同一件事的两个侧面。

### `Cargo.lock` 入库（`5e5a983`）

原本被 gitignore。后果是 CI 上依赖解析不可复现，MSRV 可被静默突破——实测发现
`proptest = "1.8.0"`（即 `^1.8.0`）会解析到要求更高 rustc 的 1.11.0。锁文件入库后，
可复现性由锁文件保证，版本约束不必到处钉死。

### `index_key` 改为 ASCII-only 小写化（`a8246ce`，FORMAT.md §2 已定稿）

`index_key = BLAKE3(normalize(path).to_lowercase())` 决定每条 index 记录的**磁盘文件名**。
`str::to_lowercase` 实现 Unicode 默认大小写转换，其映射表**随工具链版本推进**——两台机器
构建的 arca 会对同一个罕见字符路径导出不同的索引文件名，而「大小写冲突拒绝」的规则
因为两者根本不碰撞而静默失效。

这必须在 M1 写下第一条 index 记录之前定，否则就是磁盘改名迁移。赶上了。

### trace 作为 M0 交付（`e44e687`、`9b7f6f7`）

项目所有者在 M0 执行期间并行完成了 trace 设计，并要求 schema 在 M0 落地
（理由：`event` 是封闭枚举、受 I10 约束，一旦有实现开始发事件就不能再随意改）。
因此计划中途插入了 Task 12。

## 评审抓到了什么

12 个任务，**每一个**的评审都找到了真问题。摘录最有代表性的：

| 任务 | 问题 | 为什么要紧 |
| --- | --- | --- |
| manifest | 重复路径未拒绝 | `sort_by` 是稳定排序，同一组条目按不同顺序传入会序列化出不同字节——直接打穿这个格式唯一的存在理由（确定性）。按 I5 定为**拒绝**而非静默去重：静默挑一条就是禁止的「猜测」 |
| 切块压缩 | `decompress` 无解压上限 | 损坏或恶意的 zstd 帧能把内存吃到 OOM，而 fsck 正是要对磁盘上**任意**块调它 |
| 哈希原语 | `sha256_hex` 零测试覆盖 | 互操作边界（Git LFS oid、Dropbox 导入校验）上的哈希函数没有任何验证 |
| JSON Lines | journal 的 `version_id` 被当成 `Option` | FORMAT.md 的字段表对三种 op 都给了具体值，是 brief 的测试数据过时了——规范是契约，brief 不是 |
| vault TOML | `Registry` 只能解析不能构造 | M1 的 `arca init` / `arca register` 需要**生成** `.gitarca` |
| fsck | 诊断粒度把 IO 失败与内容错误折叠 | 运维看到一批 `CorruptChunk` 会以为数据烂了，实际可能只是目录权限设错 |

### 逃生舱脚本的三次假绿

同一个脚本被三次发现「该失败时却报成功」，每次都是**实际执行**发现的，不是读代码猜的：

1. `.arca/items/` 为空或缺失时报告成功——循环体一次都没执行，`files/` 里的文件从未被校验
2. 花括号配平检查误杀含 `{` 的合法 `actor` 字段，静默丢弃一个真实提交过的版本，
   然后对完好的数据发假警报
3. **脚本从不读 `format.json`**——「空 `files/` + 空 items」两个计数都是 0，`0 == 0` 通过，
   退出 0。这正是 I11 的形状（未挂载的卷被当成空库），而且发生在恢复现场，
   用户可能据此复用源盘。前两次修的假绿都要求文件数大于 0，这是它们留下的洞

教训：**一个永远返回成功的校验脚本比没有脚本更糟**——它让人以为承诺被验证过了。

### 最终全分支评审

opus 做的跨任务评审又找出 1 Critical + 10 Important，包括：四个 hub 侧格式没有 golden
vectors（字段改名能让全套测试通过却废掉磁盘上每个库）、`journal/epoch` 指针文件规范里
写了三种处置却无任何实现、`Cursor::parse` 不校验 epoch 编码（而它会变成路径片段）。
一波修完并经定向复审确认全部解决。

## 留给后续的

**已知限制（评审分诊为「可以等」）**

- FORMAT.md：键序对读取侧是否需校验未写明；紧凑时间戳无形式文法（现仅校验形状与数字性）
- `MAX_PHYSICAL_PATH_BYTES` 声明了但无处强制——M1 拼接 dataset_root 时是天然强制点
- `chunks/refs/`（§8 预留）会被 fsck 当成十六进制分片遍历，是 M2 的陷阱
- fsck 的 `CorruptChunk` / `OrphanIndex` / `BrokenChain` 三个变体无正面测试
- 块路径逻辑在 `arca_chunk::store` 与 `hub_layout::layout` 各有一份定义，基准不同
- 公开枚举未标 `#[non_exhaustive]`，与 conformance 套件的第三方实现目标有张力

**M0 的 fuzz 有一个环境局限**：本机（macOS + Apple Silicon）的 ASAN 启动即挂起，
11 个 target 是用 `--sanitizer none` 跑的。两个被 fuzz 的 crate 都 `#![forbid(unsafe_code)]`，
所以「绝不 panic」这条覆盖不受影响；唯一漏掉的是 `decompress` 背后 zstd C 库 FFI 边界的
内存安全。已加每晚 cron 的 Linux + ASAN fuzz 作业把这个缺口关掉。
