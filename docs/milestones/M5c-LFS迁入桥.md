# M5c · Git LFS 迁入桥

**完成于 2026-08-09** · 2 个提交 · 结束时 879 个测试全绿

兑现 M5 的另一条头条验收：**既有 LFS 仓库一键迁入**（spec §12.3、§8）。

---

## 风险不在解析，在覆盖

LFS 指针只有三行，解析不会出错。真正会出事的是第二步：**用一份字节覆盖掉
指针文件**。如果那份字节不是指针声称的那一份（对象缺失、被截断、被换过），
覆盖之后：

- **指针没了**——`oid` 是找回原内容的唯一线索，它就在被覆盖的那几行里；
- **内容是错的**——而且看起来像「迁移成功」。

所以核心纪律：**先校验 SHA-256 等于 `oid`，再写**；写用 tmp → rename。

具体到代码：**校验通过之前，目标文件的字节一个都不能动。** 这类代码很容易
写成「先打开目标文件准备写、再校验」——那样一个 `truncate` 就已经把指针毁了。

---

## 三种失败，各自可诊断且指针原封不动

| 情况 | 处置 |
| --- | --- |
| `.git/lfs/objects/` 下没有这个对象 | 「多半是没跑过 `git lfs pull`」，给出下一步 |
| SHA-256 与 `oid` 不符 | 报出两个哈希并说清为什么不覆盖 |
| 哈希对而 `size` 对不上 | **数学上不可能** → 说明**指针本身被改过** |

第三条值得单说：哈希对而字节数不对在数学上不可能，所以它命中时唯一的解释是
指针被人手改过。两者都验正是为了让这种情况能被**认出来**，而不是默默按哈希
放行——只验哈希的实现会把一个损坏的指针当成健康的。

---

## 绝不调用 `git lfs`

对象就在 `.git/lfs/objects/<xx>/<yy>/<oid>` 里，布局是固定的。依赖外部二进制
会让「一键迁入」变成「先装 git-lfs」——而迁入是获客的第一入口（spec §8），
多一步就少一批人。

同一条理由也用在测试夹具上：手工拼出对象布局，**测试不需要装 git-lfs**。

---

## 其余纪律

- **默认 dry-run**（与 `arca gc` 同一条）：这条命令会就地改写用户的文件。
- **有任何文件被跳过 → 退出码非 0。** 「一半迁成功了」不该看起来像全成功。
- **一个文件失败不中止整批**——一个对象缺失不该让另外 999 个迁不进来；
  用户真正需要的是一份说清「哪些好了、哪些没好、为什么」的报告（spec §8：
  「出具迁移审计报告」）。
- 符号链接不跟随（I6）；超过 4 KB 的文件直接不当指针看；
  读不成 UTF-8 的文件本来就不是指针。

---

## 验证证据

879 个测试全绿 · clippy 零告警 · rustfmt 干净 · MSRV 1.85 通过。

实机三态：正常迁入内容逐字节正确；缺对象与被篡改两种情况下**指针都原封不动**；
普通笔记未被碰；dry-run 之后目标文件仍是指针。

## 真正缺的

1. **迁入之后不会自动 `arca adopt`。** 目前是两步：先 `import lfs` 换回内容，
   再 `adopt` 纳管。合成一步更顺手，但也更难在中途出错时说清楚状态——
   现在这样每一步的失败都是局部的
2. **不清理 `.gitattributes` 里的 LFS filter 行。** 迁完之后那些
   `filter=lfs diff=lfs merge=lfs` 还在，下次 `git add` 又会把文件变回指针。
   **这是目前最大的缺口**——它会让迁入在用户下一次提交时被静默撤销
3. **不删 `.git/lfs/objects/` 里的对象。** 符合 I3（不销毁），但用户会问
   「为什么磁盘没省下来」，应当在报告里说明
4. LFS Batch API（让 arcad 冒充 LFS 服务端）属 v2，spec §8 明说「LFS 桥仅用于
   既有 LFS 仓库迁入」
