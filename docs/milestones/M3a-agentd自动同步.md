# M3a · agentd 自动同步回路

**完成于 2026-08-09** · 5 个提交 · 结束时 791 个测试全绿

M3 的第一块。`arca-agentd` 从 18 行骨架变成能真的替你同步的 daemon。

---

## 唯一重要的架构决定

**agentd 是 `arca-cli` 的消费者，不是它的平行实现。**

CLAUDE.md 的分层降级关系写着「agentd 是手动 CLI 的增强，不是依赖」，
而它在代码上的含义只有一个：**两者跑同一段代码**。决策来自 `arca-core`，
执行来自 `arca_cli::sync::sync_transport`——经由 `syncer::do_sync` 这个
可以被 grep 到的单点。`syncer.rs` 的模块文档写明：

> 本文件里**不应该出现任何 `RemoteState`/`Decision`/`Action` 的匹配**。
> 如果你发现自己在这里写「如果远端有而本地没有就下载」，你走错地方了。

理由不是洁癖。如果 agentd 自己写一套调和执行，两条路会分叉，用户报
「手动同步没事、自动同步丢东西」时**没有人能解释**——M2d 的评审在
`Transport` 上抓过同构的问题（「角色在一种传输上被尊重、在另一种上被忽略」）。

## 交付了什么

| 部分 | 内容 |
| --- | --- |
| 单实例锁 | `<vault>/.arca/agentd.lock`，`flock` 而非 pid 文件 |
| 每数据集独立回路 | 独立退避（1/2/4…封顶 60s）、独立健康度、panic 隔离 |
| `Transport::changes` | M2c 建的 `/changes` **第一次有了客户端消费者** |
| 增量游标持久化 | `<ds>/.arca/client/changes-cursor`（FORMAT.md §9.6） |
| 崩溃演练 | `kill -9` agentd 之后手动命令照常，**带对症的反面夹具**，进 CI |

### 锁在 vault 侧，不在存储根侧

`arca_store::lock` 已经有一把跨进程锁，但它落在**存储根**里——而存储根随时
可能离线（I11），agentd 恰恰需要在离线期间活着（它要负责在盘挂回来时接上）。
把单实例锁挂在一个可能不存在的目录上，等于让「能不能启动」取决于
「外置盘插没插」。

用 `flock` 而不是 pid 文件：pid 文件不会随进程死亡而失效，`kill -9` 之后留下的
pid 文件要么让下次启动误判「已经有实例在跑」，要么去 kill 一个早已被系统复用
给别人的 pid。内核在进程退出时**无条件**释放 flock，不论退出得多难看。

### `changes` 只用来**唤醒**，不用来驱动调和

按事件增量地改本地很诱人，但那等于在 agentd 里重新实现一遍调和——而正确性
全部由 `arca-core` 的 18 格决策表与四道闸门保证。事件流告诉我们的只是
**「那边有动静」**；「该怎么办」仍然交给同一段代码去算。

代价是每次唤醒做一次全量对账。收益是 agentd 与手动命令**永远不会给出不同的
结果**。真正的增量优化（只对变动路径调和）要等 `arca-core` 支持
「只看这几条路径」，那不是 agentd 该私自解决的问题。

### 两条传输的取舍

- **`ResetRequired` 是 `Ok` 的变体而不是 `Err`。** 做成错误会被 agentd 那类
  泛泛的重试逻辑吞掉，而漏掉全量对账的后果是客户端永远缺一段历史。
  与 `CommitOutcome::Conflict` 同一条纪律（M2b）。
- **`file://` 的 `changes` 忽略 `wait` 并立刻返回。** longpoll 的本质是
  「服务端替客户端等」，而 `file://` 没有服务端。可选的替代是自己轮询 mtime，
  但那只是把轮询藏进传输层：调用方以为拿到了推送语义，实际拿到的是看不见的
  忙等。**诚实的「我做不到」好过一个形似推送的轮询。**

### 游标：读不懂就当作没有

这与 I5「绝不猜测」不冲突，`cursor.rs` 的模块文档专门写清了判据：

> 判据不是「要不要猜」，而是**「猜错的代价是什么」**。
> `role.toml` 解析失败必须是错误——角色决定远端删除到达时本地副本是被移除还是
> 被保留，猜错的后果是数据没了。游标解析失败当作没有——后果只是退化成一次
> 全量对账，而全量对账本来就是这个系统的地基。

游标**只在一轮调和成功之后才推进**。中途失败保持原值，下一轮重来——宁可重复
消费一段已经处理过的事件（调和本身幂等），也绝不跳过。

## 实机验证

- **longpoll 唤醒**：起 arcad + agentd（间隔 15 秒），从另一台设备提交文件，
  设备 2 在 **1 秒内**拿到——远小于间隔，证明是被唤醒而非睡到点
- **多 hub 隔离**（判据是**字节**）：拔掉 alpha 的存储根 → beta 的新文件真的
  落进它自己的 store，alpha 被点名且说清是哪个 hub，alpha 的本地文件一个都
  没被删；盘挂回去后 agentd 自己把积压补上
- **崩溃演练**：`kill -9` 之后 `sync`/`status`/`verify` 全部照常、数据逐字节
  完好、`doctor` 干净、agentd 能重启

791 个测试全绿 · clippy 零告警 · MSRV 1.85 通过 · **`arca-core` 未改一行** ·
`arca-cli` 依赖树 tokio 节点数仍为 **0**。

## 自己抓到的三处

### 反面夹具用错了，等于没验

崩溃演练写完后我想复用 M2d 的 `fake-always-success-wrapper.sh`，**它没抓住
任何东西**——那个夹具模拟的是「I11 挂载校验失效、离线也报成功」，它强制
**成功**；而本演练的正例本来就期望成功、真正的判据是字节是否落地。

写了对症的 `fake-requires-agentd-wrapper.sh`（模拟「手动命令开始依赖 agentd」
这个具体回归），正反两面才都验过。

> **一个夹具只能证伪它模拟的那一种回归。用错夹具比没有夹具更危险：
> 它会让人以为演练被验过了。**

### 演练自己的进程语义错了

第一版在第 6 步以「锁泄漏了」失败。`pgrep` 之后才看清是脚本的问题：
`kill -9` 打的是子 shell，agentd 作为孤儿活着，**锁正确地拒绝了第二个实例**。
加 `exec` 让 `$!` 指向 agentd，并补一条 `kill -0` 断言确认它真的死了——
否则后面几步测的是另一回事，还会以一条误导的信息失败。

### `--once` 从不落盘游标

实机跑出来的：`--once` 直接 `return`，跳过了游标推进。于是每次脚本化调用
（演练、CI、cron）都从头做一次全量对账，更糟的是——**游标持久化这条路径
也就永远不会被这些流程走到**。一个只在长驻模式下才生效的持久化，等于一个
没被日常验证覆盖的持久化。已修并补了三条集成测试。

## 真正缺的，按优先级

1. **本地 watcher 尚未实现**（M3b）——本地侧变更目前靠周期扫描发现，
   spec §5.2 三重保险只有最后一层。远端侧已经是 longpoll 推送了，
   两侧的延迟不对称
2. **每次唤醒做一次全量对账**——见上文的取舍。大库上这会成为 CPU 与 IO 的
   常态开销，真正的解法要 `arca-core` 支持「只对这几条路径调和」
3. **`arca status` 看不见 agentd**——用户没法一眼知道「自动同步在不在跑、
   上次成功是什么时候」。`ipc.rs` 仍是骨架
4. 退避**没有随机抖动**——本项目形态（个人几台设备对自己一台 NAS）下不需要，
   但多客户端共用 hub 的场景出现时要加，并同时给测试注入随机源

### M3d 的环境依赖（如实记录）

`arca-winfs` 是 Windows-only 的 CfAPI FFI，也是全项目**唯一的 unsafe 边界**。
在 macOS 上可以写出代码，但无法编译、无法运行、无法证明它对——而本项目一贯
的验收标准是实机攻击而不是读代码。交付未经运行的 FFI 并称之为「完成」不符合
这个标准。同理适用于 M4 的 `arca-macfs`（Swift + File Provider，且不在 cargo
workspace 内）。这两块需要各自的目标平台环境才能真正推进。
