# M3c · 分级驻留策略与水化调度

**完成于 2026-08-09** · 3 个提交 · 结束时 832 个测试全绿

落地 spec §4.8，并把 §6.3 第 7 条那条 ★ 必过测试做成可执行的形态。

---

## 先说清楚这一块**没有**做什么

**本切片交付的是策略，不是占位符。** 没有 OS 占位符层，`client` 角色仍然
全量物化，**磁盘一个字节都没省**。这里定的是「等占位符接上之后，谁该被
驱逐、什么访问该拉多少」。

这句话写在归档最前面是有原因的：写完策略引擎 + 队列 + `Provider` trait
之后，很容易在总结里说「分级驻留已实现」，而下一个人会以为 M3d 只剩
「接个 API」。实际剩下的是整个 CfAPI FFI。

---

## spec §4.8 的立场

> **占位符是给「大而冷」的文件用的，不是给所有文件用的。**

这一条把 iCloud/OneDrive 式体验的最大失败模式挡在门外：一篇内嵌 30 张图的
笔记逐个读取 → 30 次阻塞式网络拉取；编辑器全库索引/备份/杀毒扫描 →
全库水化，瞬间拉爆磁盘与带宽。

## 交付了什么

| 部分 | 内容 |
| --- | --- |
| `Intent` | `Metadata` / `Head{bytes}` / `Full`——**整条防线的入口** |
| `decide` | 纯函数，穷举无 `_ =>` 兜底 |
| `always_resident` / `may_evict` | 8 MiB 阈值、pin、14 天热度窗口 |
| `Queue` | 重复请求合并、并发上限（默认 4）、满即拒绝 |
| `Provider` trait | 占位符层的抽象边界 |
| `FullMaterialization` | spec §3.1 强制的降级路径，**生产实现** |

### 策略引擎是纯函数，不做 IO

与 `arca-core` 的 sans-io 同一条理由：**M3d 的 CfAPI 与 M4 的 File Provider
必须跑同一段判断**。不先划这条边界，策略会被分别抄进两套回调里各自漂移，
「为什么 Windows 上不水化、Mac 上水化」将变成一个没人能回答的问题。

### 一处刻意的设计：`decide` 没有 `Policy` 参数

「这次访问取不取、取多少」只取决于**意图**与**内容在不在本地**——与 8 MiB
阈值无关。阈值管的是另一个问题：**谁该常驻、谁可以被驱逐**。

把两者搅在一起是个很自然的错误：会写出「小文件就算没在本地也直接
`FetchFull`」这种看似合理的规则，而它**恰好破坏 §6.3 第 7 条**——一次全库
`stat` 会把所有小文件拉下来，字节数不再是 0。

这个参数第一版是有的（只是没用到）。删它不是消 lint，是把这条区分写进类型。

### `ensure_local` 返回字节数而不是 `()`

§6.3 第 7 条数的就是它。一个「先读整个文件再切一段」的实现如果只返回
range 长度，测试会通过而**真实故障模式原封不动**。所以 trait 上返回的
必须是「真的从 hub 读了多少」。

### 全量物化的 `evict` 明确拒绝

全量物化承诺的就是「本地永远有完整数据」，一个会驱逐的全量物化是自相
矛盾的。静默成功更糟——调用方会以为空间释放了，而磁盘一个字节都没少（I5）。
拒绝次数留痕供诊断（「这台机器上 LRU 一直在空转」）。

## §6.3 第 7 条：全库索引水化字节数 = 0

两个层次都验了：

1. **决策层**：1000 个文件的混合库（小图/中等 PDF/大视频/RAW），
   每个发一次 `Metadata`，累计 `fetch_bytes` 断言为 0。
2. **执行层**：同一批文件走 `Provider::walk`，用一个**会如实记账**的假占位符
   实现去数——而不是靠 `FullMaterialization` 恒返回 0 蒙混过关。

缩略图场景同样两层：每个文件读前 4 KB，断言**没有一个**变成 `FetchFull`，
总量被 4KB×N 界住而不是几百 GB。

**并配了反面断言**，两条：

- 把 `Metadata` 换成 `Full` 去算 → 字节数必须暴涨。如果这条也是 0，
  说明判据（`fetch_bytes`）本身失效，上面那条必过测试证明不了任何事。
- 记账实现换成 `Intent::Full` 遍历 → 总量必须等于全部文件大小之和。

> 本项目已被「只验负例」这个形态咬过四次（M0 逃生舱三次、M3a 反面夹具一次、
> M3b watcher 一次）。一条必过测试如果不同时验「判据本身有效」，
> 它和没有是一样的。

## 真正缺的，按优先级

1. **占位符层本身**（M3d/M4）。策略与边界就位了，OS 那一侧还没有
2. **策略引擎没有生产调用者**。`hydration`/`provider` 两个模块目前挂着
   `#![allow(dead_code)]`——这是「先定判断、后接 OS」的必然结果，但它意味着
   **这些判断至今没有在真实数据流里跑过一次**。M3d 接上时这个 allow 应当删掉，
   如果那时发现 trait 形状不对，改的是这里而不是 CfAPI 回调
3. **热度预取尚未实现**。§4.8 说「最近打开笔记的同目录附件预取并保持热」，
   目前只有 `days_since_access` 这个输入字段，没有产生预取动作的那一侧
4. **队列没有优先级**。用户刚双击的那个视频与后台预取排在同一条队里；
   §4.8 实现要求 3 提到「向 OS 报告进度」，那也还没有
