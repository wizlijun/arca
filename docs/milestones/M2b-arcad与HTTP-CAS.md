# M2b · arcad 与 HTTP CAS

**完成于 2026-08-08** · 4 个提交 · 结束时 581 个测试全绿（M2b 新增 69 条）·
`arcad` 3007 行

M2 的第二块，也是**全系统第一个常驻进程**——以及**项目第一次面对不可信输入**。
此前一切都在本地：一个读自己文件系统的 CLI。`arcad` 现在接受来自任何地方的请求。

## 交付了什么

| 部分 | 内容 |
| --- | --- |
| `Transport` trait（客户端） | 客户端看 hub 的唯一接口；`file://` 是它的第一个实现 |
| `PROTOCOL.md` §1.2 | 端点表、请求/响应格式、状态码——**先于实现定稿**（I10） |
| `arcad` | HTTP 服务端：挂载检查 → 503、读取端点与条件请求、CAS 写入端点 |
| `arca_store::lock` | 跨进程排他锁（`flock`/`LockFileEx`） |

### 为什么先抽传输、再写服务端

M2a 的评审建议把第 4 道闸门的接口抽成「内容此刻是否可取回（附哈希）」。
这条对整个客户端侧都成立——`hub.rs`、`sync.rs`、`gates.rs`、`trash.rs` 当时全在
直接摸文件系统。**先抽 `Transport`、让 `file://` 成为第一个实现**，HTTP 就只是第二个；
反过来做，要在写 HTTP 的同时改所有调用点。

Task 1 是**纯重构**，判据很硬：512 条既有测试**一条不改**全部通过。做到了。

### 两个形状上的坑，都躲开了

- **`CommitOutcome::Conflict` 是 `Ok` 变体不是 `Err`**。M1b 在 `into_result` 上踩过这个——
  一个冲突文件会中止整轮 sweep。`PROTOCOL.md` §7 对 `class=protocol` 的定义是
  「走结构化冲突流程，**不作为错误处理**」。
- **`Transport` 是同步 trait**，所以 CLI 不会被迫引入 tokio。spec §3.1 的
  「客户端零常驻」是形态约束——为发三个 HTTP 请求启动一个 tokio 运行时违背它。

### CAS 的两个校验器分得很清楚

`If-Match` 认**版本号**（CAS），`ETag` / `If-None-Match` 认 **BLAKE3 哈希**（缓存），
**绝不混用**。理由是 M1b 那个 412 死循环：`VersionId` 是时间戳+随机数、不由内容派生，
用哈希做 CAS 会让「同内容重新上传」反复提交过期 parent。

实现者定协议时最初写的是 `If-Match: *` 表示「仅当不存在时创建」，
自己查 RFC 9110 §13.1.2 后**发现方向反了**——`If-Match: *` 是「当前有任何表示时」，
`If-None-Match: *` 才是「不存在时」。这种在规范上主动核对而非照直觉写的习惯正是 I10 要的。

## 评审抓到了什么

切片评审做了**约 60 次实机攻击**（真的起服务、真的发请求）。

### 守住的部分

| 面 | 结果 |
| --- | --- |
| 路径逃逸 | **20/20 全拒**：字面 `../`、`%2F` 单/双重编码、overlong UTF-8、反斜杠、NUL、超长、超深、RTL 覆盖字符。`path_rules::check` 在任何文件系统操作**之前**、且对**解码后**的路径执行 |
| I11 挂载缺失即离线 | **13/14**：根被删/`format.json` 删除或损坏/身份是别的数据集/根被换成普通文件/根符号链到别的根/权限撤销——全部 503 且 **code 可区分**；且**一个数据集离线不影响其它数据集** 14/14 |
| CAS 绕过 | **12/12 全拒**：缺条件头、`If-Match: *`、拿内容哈希冒充版本号、带引号/列表/空值、两个条件头并存 |
| 并发 | 8 个真实 socket 并发创建 ×12 轮 → **恰好 12 个 201 + 84 个 412**，无双赢、无 500 |
| 薄壳纪律 | `arcad` 里**没有第二套决策阶梯**——每处 `match RemoteState` 都是序列化或状态码映射 |

### C1：`Arca-Item-Id` 是未校验的不可信输入

**根因一句话：arcad 校验了客户端声称的「版本」，却从没校验它声称的「身份」。**

三个已验证的利用：

1. **两个 HTTP 请求永久搞坏一个数据集。** 同一个 `item_id` 打两个不同路径 →
   追加出两条 `parent:null` → `parse_chain` 失败 → 该数据集**每个端点永久 500**，
   而且 `arca sync`/`status`/`doctor` 一起挂（共用 `read_remote`）。
   `GET /state` 会公布每个 `item_id`，**连猜都不用猜**。
2. **丢失的写入被确认为成功。** 复用一个已 tombstone 的 `item_id` + `If-None-Match: *`
   → 返回 **201**、字节写入、文件**永远不可见**（GET 404，`/state` 仍是 tombstoned）。
   `hub.rs` 的文档**假设**了「tombstone 过的 item 不会复活」，但没有任何东西对
   不可信输入强制它。**把这个 201 记进基线然后丢掉本地副本的客户端会丢数据。**
3. **张冠李戴的 tombstone。** DELETE 带伪造 `item_id` → 204，`.meta` 与 journal
   记下客户端给的 id，I8 的审计链被伪造。（M2a 的第 4 道闸门失败安全，后果被控制住。）

修法三条：写路径上从索引解析出该 path **真正归属**的 `item_id`，不一致即 409；
拒绝对「链非空或已 tombstone 的 item」做 `parent:None` 提交；
版本链的 `parent` 从**该 item 自己的链尾**推导，而不是从路径的当前版本。

### C2：单个请求可以占掉几 GB 内存

写侧用 axum 的 `Bytes` 提取器整体缓冲、`to_vec()` 再复制一份；
读侧**完全没有上限**——`read_content`（整文件 `fs::read`）在 Range 分支**之前**就被调用。

实测：600 MB PUT → RSS **6 MB 涨到 1.86 GB**；对 800 MB 文件做 **1 字节** Range GET
→ **824 MB**；连被拒的 1.2 GB PUT 都先涨到 1.2 GB 才返回 413。而且没有任何并发上限或超时。

与 spec §1.1 目标 9（**弱硬件友好、内存占用平稳可预测**）直接矛盾——
1 GB 内存的 ARM NAS 上，一次普通照片库上传就 OOM。

改成流式接收 + 增量哈希、Range 用 `seek` + 有界读、加并发信号量与请求超时之后：

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 200 MB PUT | — | RSS **+48 KB** |
| 600 MB PUT（超新上限） | +1.86 GB | RSS **+592 KB**，0.33s 内 413 |
| 200 MB 文件的 1 字节 Range GET | +824 MB（800MB 文件） | RSS **+32 KB** |

**内存与请求大小基本脱钩。**

### 四条 Important

- **ETag 与响应体来自两个来源，无一致性校验**——而且**不需要崩溃就能触发**：
  经由 I1 明确鼓励的逃生舱手工编辑 `files/` 里的文件，arcad 就用**旧哈希**服务**新字节**，
  客户端 `If-None-Match` 重新验证**永远拿到 304**。改为按磁盘实际 size 与记录比对，
  不一致才现场重算
- **500 响应发的 `code:"internal"` 没在 §7 注册**，而且它是最常见真实故障
  （内容缺失、链损坏、`EACCES`）返回的码——那些都是 `needs_human` 不是 `bug`
- **`arca.lock` 根本不存在**：`PROTOCOL.md` §1.1 声称 `file://` 的排他由它保证，
  但代码库里只有 §7 的 `lock.busy` 码。给了实现者退路（做实 or 如实改文档），
  它**选了做实**——`fs4` 的 `flock`/`LockFileEx`，并接进 arcad 与 `file://` 同步两个消费者
- **`.arca/index/` 缺失时返回 `200 []`**——对全新的根是对的，但对**内容还在、
  索引被抹掉**的根就成了「报告空库」，正是 I11 要防的形状，现在可经网络触发

## 留给 M2c / M2e 的四条接口缺口

评审逐条列出，写 M2c 的计划时要正面处理：

1. **没有按哈希寻址的读**——`arca cat <hash>`（PROTOCOL §5）没有 HTTP 对应，
   只有按路径的 `GET /files/{path}`
2. **没有批量提交**——每个文件一次往返，而 `sync.rs` 本地已经用 `atomic::Batch`
   与 `AppendBatch`。1 万文件的 sweep 会变成 1 万次往返
3. **`Transport` 没有 Range/续传方法**——服务端已实现并验证过的 206 经 trait 够不着
4. **`read_content -> Vec<u8>` 强制客户端也整文件缓冲**——C2 的镜像。
   两端要一起修，否则 M2e 会在客户端继承同样的内存曲线，
   而 spec §3.1 刻意让客户端保持轻量
