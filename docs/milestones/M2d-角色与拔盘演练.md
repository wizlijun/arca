# M2d · 副本角色、多 hub 故障域与拔盘演练

**完成于 2026-08-09** · 6 个提交 · 20 个文件、2269 行新增 · 结束时 685 个测试全绿

**M2 的收口。** 切片评审结果是**零 Critical**。

---

## 这块闭合了什么

spec §4.7 的一句话：

> **server 承诺「本地永远有完整数据，任何云侧语义都不会缩减它」；client 把本地视为
> 可再生缓存。只要任一 server 副本存活，数据就在自己手里。**

在这之前，**所有绑定都被当成 client 角色对待**——过了四道闸门就 `fs::remove_file`。
一个把外置大盘当离线备份的用户，会发现他的备份跟着云侧语义一起缩水。
对归档产品来说这是最不能接受的结果。

---

## 交付了什么

| 部分 | 内容 |
| --- | --- |
| `role.toml` | server/client，**设备本地决策，不进 git**（`<ds>/.arca/client/`） |
| 角色分流删除的执行侧 | client 移除本地副本；server 移进工作区侧本地 trash |
| 多 hub 独立故障域 | 一个 hub 不可达只让它的数据集离线，其余照常同步 |
| 已知 server 副本数告警 | spec §4.5 的 numcopies，致敬 git-annex |
| **拔盘演练** | 自动化脚本 + CI，含**反面夹具** |

### 关键分工：`arca-core` 不认识角色

决策表仍然给出 `DeleteLocal`；**角色只在执行侧分流**成「移除」还是「移进本地 trash」。
`arca-core` 全程一行未改。

评审专门核实了这不只是结构上的说法：`sync()` 与 `sync_transport()` 都调用**同一个**
`execute_delete_local`，并且它真的起了一个 `arcad` 把整个场景在 `http://` 上重跑了一遍——
两种传输语义完全相同。**角色在一种传输上被尊重、在另一种上被忽略**，正是
`Transport` 抽象当初要消除的那类分叉。

### 默认角色定为 `client`

举证责任在「声明 server」那一侧——那是「永不主动释放空间」的强承诺。
默认 client 永不过度承诺，符合 I5「往保守一侧猜」，也保持了既有数据集的行为不变。

## 拔盘演练：这次它有牙齿

spec §12.3 的 M2 验收点名要求「**拔盘演练：卷离线呈现为数据集离线而非空库（I11）**」。

M0 的逃生舱脚本曾被评审**三次**抓到「该失败时报成功」。这次实现者主动写了一个
**反面夹具**——一个强制 `status`/`sync`/`verify` 永远退出 0 的包装脚本，
模拟「I11 校验失效」这个具体回归。**用它跑演练，演练必须失败。**

我自己验了正反两面：正例端到端通过；反面运行退出 1 并点名
「status 在盘被拔走之后仍然报成功——I11 校验失效，这正是本演练要抓的反面」。

评审又用另外四种方式削弱实现，**四种全被抓住**：

| 削弱方式 | 是否被抓 |
| --- | --- |
| 拔盘期间本地文件被删 | ✅ 第 4 步 |
| 报了非零但诊断里不说「离线」 | ✅ 第 3 步（诊断必须点名原因） |
| adopt 后清空 hub 的 `files/` 与 `index/` | ✅ 第 1 步 |
| 拔盘窗口内 arca 什么都不管（空库） | ✅ 第 7 步 |

CI 每次 push/PR 都跑两个演练加反面夹具，不是每晚。

## 评审抓到了什么

**零 Critical。** 评审驱动真实二进制做了完整攻击：

- **server 角色确实保住数据**：role.toml 中途损坏 → sync 退出 1 且待删文件**存活**
  （角色在调和循环之前读一次，读坏就整轮中止，正确的 I5 行为）；
  本地 trash 写入失败 → 中止于 `baseline.remove` 之前，工作区文件完好
- **多 hub 隔离用字节验证**：三个数据集分属三个 hub，破坏其一后**断言健康数据集的
  新文件真的落到了它自己的 store 里**，不只看退出码；并确认坏掉的 hub
  **没有污染那个数据集的基线**（未同步的本地改动没被误记为已同步）

两条 Important 都在副本数告警，不在数据安全核心：

- **副本告警让干净的默认角色数据集 `arca status` 退出 1**。这破坏了 PROTOCOL.md
  记载的三态语义（1 = 命令本身的失败），让 `status` 在默认配置下无法回答
  「是不是都同步好了」，而且**反过来逼用户去声明 `server`**——那是强承诺——
  只为消掉一个退出码。最能说明问题的是：**这个切片自己的演练脚本里专门
  `role server`**，就是为了让告警不污染 `assert_clean`。改成打印告警但不动 `level`
- **副本告警对 `http://` hub 从不触发**——也就是整个 M2b/M2c 的主线配置。
  而那道 gate 是不必要的：`known_server_copies` 只读 `role.toml`，从不碰 `StorageRoot`

## M2 收官评估（评审结论）

对照 spec §12.3 的 M2 行，**M2 实质完成**。a/b/c/d 各自交付了验收证据，
M2d 用两件 M2 真正要负责的东西收口：一个**带已证明会失败的反面夹具**的可执行 I11 演示，
以及用**字节**而非退出码验证的客户端侧独立故障域。

「先建立绝不丢数据的信誉」这条排序原则守住了——**本切片对销毁路径的净效果是负的**
（server 角色移除了一次 `unlink`，没有新增任何一个）。

### 真正缺的，按优先级

1. **本地 trash 是只写的。** spec §4.7 说 server 角色的 tombstone「移入本地 trash
   **保留期**，物理销毁只经显式 GC」——但目前没有保留期概念、没有 GC、
   没有 `arca restore` 通路、没有列表、`doctor` 也看不见它。今天恢复要手读
   `.data`/`.meta`。`FORMAT.md` §9.5 与 `local_trash.rs` 已经诚实地划出了范围，
   所以不是毁诺——**但 server 设备的 trash 会无界增长**。
   **这是最大的一条 carry-forward。**
2. **`arca status` / `doctor` / `verify` 仍是 `file://` only。** 而 arcad 是 M2 的主线，
   主健康检查命令对主 hub 类型不工作
3. **副本计数看不到其它设备**——告警文案已诚实披露，需要 hub 侧登记绑定，正确地推后了

## Readiness for M3（评审结论）

**角色抽象的形状是对的——M3 加「dehydrate」是加法不是重塑。** 三条理由：

1. 分流只在**一个函数**里（`execute_delete_local`，两个引擎都走它），
   M3 的驱逐挂在执行侧而不必碰决策
2. `arca-core` 真的不认识角色——决策表仍发 `DeleteLocal`，四道闸门对角色无感，
   sans-io 状态机保持共用
3. **最重要的**：M3 的驱逐是**不同的触发器**而不是本触发器的变体——
   LRU/pin 驱逐根本不由远端 tombstone 驱动，所以它需要一个新入口而不是这个 `match` 的新臂

`Role` 的 `parse() -> Option` 与 `schema > MAX_SCHEMA` 硬停意味着 §4.8 的驻留策略字段
可以按 I10 以 `schema = 2` 落地而不破坏老读者——它们会拒绝而不是猜测。
