# M3b 本地 watcher（变更检测三重保险）实现计划

**Goal:** 补齐 spec §5.2 的客户端变更检测三重保险——目前只有第三层
（周期性全量对账），本地改动最多要等一个间隔才被发现。

**Architecture:** watcher 只产生**唤醒信号**，不产生变更清单。三层的分工是
「谁先发现」，不是「谁来判断」——判断永远是 `arca_cli::sync` 那一次全量扫描对账。

**Tech Stack:** Rust 2021 / MSRV 1.85 · `notify`（跨平台文件系统事件） · 已有的 agentd

---

## 三重保险的真实含义

spec §5.2：

> 客户端变更检测三重保险继承 Lazync §5：实时事件（Windows `ReadDirectoryChangesW` /
> macOS FSEvents）→ **溢出即全扫** → 周期性全量对账地基。

关键在中间那一层。**实时事件是不可靠的**——内核缓冲区会溢出，事件会被合并、
丢弃、乱序；网络盘、容器挂载、某些文件系统根本不发事件。任何把实时事件
当作**真相**的设计都会静默丢改动。

所以本切片的纪律是：**watcher 说「有动静」，全量扫描说「动了什么」。**
watcher 送来的路径信息一律**只用于日志**，绝不用于决定同步什么。
这与 M3a 对 `changes` 的处理是同一条纪律（「只用来唤醒，不用来驱动调和」），
理由也一样：判断一旦有第二个来源，两个来源就会分叉。

## Global Constraints

- MSRV **1.85**。**每个任务自己跑完四项门禁再交**。
- `#![forbid(unsafe_code)]`。**`arca-core` 一行不改**。
- tokio 只允许在 `arcad` 与 `arca-agentd`。`arca-cli` 的 tokio 节点数必须仍为 **0**。
- 只在 `main` 分支。提交信息、文档、注释一律中文。
- **watcher 失败必须降级而不是中止**——某些平台/文件系统不支持事件监听，
  那时 agentd 必须退回纯周期模式并说明，绝不因此拒绝启动
  （分层降级关系：watcher 是周期对账的增强，不是它的替代）。
- **绝不监听 `.arca/` 内部**——agentd 自己写基线、游标、trash 都在那里面，
  监听它会造成自我唤醒的无限循环。这是本切片最容易炸的地方。

### Task 1: watcher 骨架与降级

**Files:** `crates/arca-agentd/src/watcher.rs`

- [ ] `Watcher::start(paths) -> Result<Watcher, WatchError>`，事件经
      `tokio::sync::mpsc` 送出。**只送「有动静」，不送路径清单**
      （路径可以带上供日志用，但类型上要让人一眼看出它不参与决策）。
- [ ] **不支持时明确降级**：`start` 失败 → agentd 打一句「本数据集退回周期模式，
      原因 X」并照常跑，退出码不受影响。
- [ ] **忽略 `.arca/`**：agentd 自己的写入不得触发唤醒。测试必须**直接断言**
      「往 `.arca/client/baseline.jsonl` 写入不产生唤醒」——这是自我唤醒
      无限循环的唯一防线。
- [ ] 去抖：短时间内的连续事件合并成一次唤醒（默认 500ms）。
      编辑器保存一个文件常常产生 3–10 个事件（写临时文件 → rename → chmod）。

### Task 2: 接进 agentd 的等待循环

**Files:** `crates/arca-agentd/src/main.rs`、`syncer.rs`

- [ ] 等待时同时盯三路：本地 watcher 唤醒 / 远端 longpoll 唤醒 / 周期到点 / 停止信号。
- [ ] **三者任一到达都只做一件事：跑一轮全量调和。** 不因为「是本地事件」
      就只上传、不因为「是远端事件」就只下载——那是在 agentd 里重建决策。
- [ ] 退避期间**不接受 watcher 唤醒**：一个连不上的 hub，本地每存一次盘就重试
      一次，等于把退避架空（M3a 已对 longpoll 做了同样处置）。
- [ ] 测试：改一个本地文件 → agentd 在**远小于周期间隔**的时间内同步它
      （断言字节 + 断言耗时，两者缺一不可——只断言字节证明不了是被唤醒的）。

### Task 3: 溢出即全扫

**Files:** `crates/arca-agentd/src/watcher.rs`

- [ ] `notify` 报告事件丢失/溢出时，**不是错误**：它正是三重保险第二层存在的
      理由。处置是「立刻触发一次全量调和」并留一句日志。
- [ ] 测试：注入一个溢出事件 → 断言产生了唤醒（而不是被吞掉）。

### Task 4: `arca status` 看得见 agentd

**Files:** `crates/arca-agentd/src/ipc.rs`、`crates/arca-cli/src/commands/porcelain.rs`

M3a 归档列的第 3 条 carry-forward：用户没法一眼知道「自动同步在不在跑、
上次成功是什么时候」。

- [ ] agentd 把心跳写进 `<vault>/.arca/agentd-status.json`（**先写 `FORMAT.md`**，I10）：
      pid、启动时刻、每数据集的上次成功时刻/上次错误/watcher 是否在用。
- [ ] `arca status` 读它并报告。**读不到不是错误**——手动模式是基线，
      agentd 没在跑是完全正常的状态，措辞不能暗示「你应该起一个 agentd」。
- [ ] 心跳文件**过期即视为不可信**（agentd 被 `kill -9` 时来不及清理）：
      超过 N 倍心跳间隔就报告「agentd 可能已不在运行」，绝不拿着一个
      三天前的心跳说「自动同步正常」。

## Self-Review

**最容易炸的是 `.arca/` 自我唤醒。** agentd 每轮都写基线与游标；如果 watcher
监听了它们，就是一个 100% CPU 的死循环，而且它在小库上「看起来能用」——
只有在真机上跑一会儿才显形。测试要直接对着这条断言。

**第二容易错的是把 watcher 事件当真相。** 任何「既然事件告诉我们改的是 a.txt，
那就只同步 a.txt」的优化都会丢改动（事件会被合并/丢弃）。三重保险的第二层
存在的全部理由就是承认第一层不可靠。
